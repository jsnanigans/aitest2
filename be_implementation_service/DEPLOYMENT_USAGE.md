# Weight Processor AWS Lambda - Deployment Usage Guide

## Overview

The Weight Processor is deployed as an AWS Lambda function that processes weight measurements using Kalman filtering and adaptive quality scoring. The function is invoked directly (no API Gateway) via AWS Lambda invoke API.

**API Version:** 2.0.0

### Get Function Name

The Lambda function name is auto-generated by CloudFormation. To get the function name after deployment:

```bash
# Get function name from stack outputs
aws cloudformation describe-stacks \
  --stack-name WeightProcessorDevUs \
  --query 'Stacks[0].Outputs[?OutputKey==`FunctionName`].OutputValue' \
  --output text

# Or use the exported value
aws cloudformation list-exports \
  --query 'Exports[?Name==`weight-processor-function-name-dev-us`].Value' \
  --output text

# Set as environment variable for easy use
export FUNCTION_NAME=$(aws cloudformation describe-stacks \
  --stack-name WeightProcessorDevUs \
  --query 'Stacks[0].Outputs[?OutputKey==`FunctionName`].OutputValue' \
  --output text)
```

**Naming Pattern:**
- Format: `{StackName}-WeightProcessorFunction-{RandomString}`
- Example: `WeightProcessorDevUs-WeightProcessorFunction-Ab1Cd2Ef3Gh4`

**Event Payload:**
```json
{

        "uuid": "measurement-id-1",

      "fail_on_conflict": true,
      "include_debug_info": false

}
```

**Parameters:**
- `measurements` (required): Array of weight measurements
  - `uuid` (required): Unique measurement ID
  - `weight` (required): Weight value (positive number)
  - `unit` (required): Unit of measurement (kg, lb, lbs, g, oz, st)
  - `effectiveDateTime` (required): ISO 8601 timestamp
  - `source` (required): Data source identifier
  - `metadata` (optional): Additional metadata
- `options` (optional): Processing options
  - `force_replay` (default: false): Force replay mode
  - `fail_on_conflict` (default: true): Fail on historical conflict
  - `include_debug_info` (default: false): Include debug information
- `user_height_m` (optional): User height in meters (0-3.0)

### 5. Replay Measurements

Execute replay from a specific timestamp with measurements.

**Important:** You must provide ALL measurements to replay. The Lambda does not store historical measurements. Your client system must store and query measurements for the replay window.

**Note:** Replay uses the same quality scoring as regular processing. Historical measurements may be rejected if they don't meet quality thresholds during replay.

**Event Payload:**
```json
{
  "action": "replay",
  "user_id": "user-123",
  "body": {
    "replay_from_timestamp": "2025-09-25T00:00:00Z",
```

**Parameters:**
- `replay_from_timestamp` (required): ISO 8601 timestamp to replay from

## Configuration

### Supported Weight Units

The following units are accepted in the `unit` field:
- `kg` - Kilograms
- `lb`, `lbs` - Pounds
- `g` - Grams
- `oz` - Ounces
- `st` - Stones

**Note:** Full word units like "kilogram", "kilograms", "pound", "pounds" are NOT supported. Use abbreviations only.

### Quality Scoring Components

The service evaluates measurements using multiple criteria (weights sum to 1.0):
- **Kalman Fit** (40%): How well measurement fits Kalman prediction
- **Temporal Consistency** (30%): Change rate validation
- **Anomaly Detection** (20%): Statistical outlier detection
- **Source Reliability** (5%): Weighted by data source type
- **Trend Alignment** (5%): Alignment with trend direction

**Quality Threshold:** 0.46 (configurable)

### Kalman Filter Parameters

Default configuration from `config.toml`:

```toml
[kalman]
initial_variance = 0.364
transition_covariance_weight = 0.018
transition_covariance_trend = 0.00012
observation_covariance = 5.0
```

### Adaptive Reset Types

The system uses three types of adaptive resets:

1. **Initial Reset** - First measurements for a user
   - Higher variance and noise to adapt quickly
   - Adaptation period: 10 measurements or 10 days

2. **Hard Reset** - After long gaps (>30 days)
   - Moderate increase in variance
   - Adaptation period: 10 measurements or 7 days

3. **Soft Reset** - After significant weight changes (>5kg)
   - Triggered by specific sources (questionnaire, care-team-upload)
   - Smaller variance adjustment
   - Adaptation period: 15 measurements or 10 days

### Replay Configuration

From `config.toml`:

```toml
[replay]
enabled = true
buffer_hours = 24
trigger_mode = "time_based"
max_buffer_measurements = 100
state_history_limit = 100

[replay.outlier_detection]
iqr_multiplier = 1.5
z_score_threshold = 3.0
temporal_max_change_percent = 0.5
min_measurements_for_analysis = 2
```

## Usage Patterns

### Single Measurement Processing

Process measurements one at a time for real-time filtering:

```bash
# Process single measurement
aws lambda invoke \
  --function-name $FUNCTION_NAME \
  --region us-east-1 \
  --payload fileb://measurement.json \
  response.json

# View results
cat response.json | jq '.data'
```

### Batch Processing

Process multiple measurements sequentially. For optimal replay support, invoke once per measurement:

```bash
# Process measurements in chronological order
for file in measurements/*.json; do
  aws lambda invoke \
    --function-name $FUNCTION_NAME \
    --region us-east-1 \
    --payload "fileb://$file" \
    "response_$(basename $file)"

  # Small delay to ensure sequential processing
  sleep 0.1
done
```

### Replay Workflow

Replay allows reprocessing measurements from a specific timestamp:

```bash
# Execute replay with measurements from your database
aws lambda invoke \
  --function-name $FUNCTION_NAME \
  --region us-east-1 \
  --cli-binary-format raw-in-base64-out \
  --payload '{
    "action": "replay",
    "user_id": "user-123",
    "body": {
      "replay_from_timestamp": "2025-09-25T00:00:00Z",
      "measurements": [
        {
          "uuid": "measurement-id-1",
          "weight": 185.5,
          "unit": "lb",
          "effectiveDateTime": "2025-09-25T10:00:00Z",
          "source": "smart_scale"
        },
        {
          "uuid": "measurement-id-2",
          "weight": 184.8,
          "unit": "lb",
          "effectiveDateTime": "2025-09-26T10:00:00Z",
          "source": "smart_scale"
        }
      ],
      "user_height_m": 1.75
    }
  }' \
  replay_response.json

# View results
cat replay_response.json | jq '.'
```

**Important:**
- You must query and provide ALL measurements from your database for the replay window
- Measurements should be in chronological order by `effectiveDateTime`
- The Lambda does not store historical measurements

## Security

### Authentication & Authorization

The Lambda function uses **IAM role-based authentication** with the backend ECS task role for security.

**Key Configuration:**
- **Authorized Principal**: Backend ECS task role (e.g., `BackendDevUs-TaskRole`)
- **Lambda Function ARN**: Available from stack outputs
- **Permission Type**: Backend task role must have `lambda:InvokeFunction` permission in its IAM policy

**How to Invoke from Backend Application:**

The backend ECS task role must be configured with `lambda:InvokeFunction` permission for the weight processor function ARN. From your backend application running in ECS:

```bash
# Get function ARN from stack outputs
export FUNCTION_ARN=$(aws cloudformation describe-stacks \
  --stack-name WeightProcessorDevUs \
  --query 'Stacks[0].Outputs[?OutputKey==`FunctionArn`].OutputValue' \
  --output text)

# Invoke using the ECS task role credentials (automatically available in ECS)
aws lambda invoke \
  --function-name $FUNCTION_ARN \
  --region us-east-1 \
  --cli-binary-format raw-in-base64-out \
  --payload '{"action": "health"}' \
```

## Best Practices

### 1. Sequential Processing
Process measurements in chronological order for optimal Kalman filtering. Sort by `effectiveDateTime` before invoking.

### 2. Use Canonical Field Names
While aliases are supported (e.g., "uuid" for "measurement_id"), prefer the canonical field names from API v2 for consistency.

### 3. Unit Consistency
Always provide explicit units using abbreviations only:

**✓ Good:**
```json
{"weight": 185.5, "unit": "lb"}
```

**✗ Bad:**
```json
{"weight": 185.5, "unit": "pounds"}  // Not supported!
{"weight": 185.5}  // Missing unit will be rejected
```

### 4. State Management
Use `cleanup` with appropriate cleanup_type:
- `reset_adaptive` - For resetting adaptation parameters
- `clear_all` - For complete state reset (pregnancy, medical procedure, etc.)

### 5. Error Handling
Always check the `success` field before processing results:

```bash
if [ "$(cat response.json | jq '.success')" = "true" ]; then
  # Process data
  cat response.json | jq '.data'
else
  # Handle error
  cat response.json | jq '.error'
fi
```

### 6. Replay Workflow
For replay operations:
1. Query your database for all measurements in the replay window
2. Sort measurements chronologically by `effectiveDateTime`
3. Invoke the `replay` endpoint with all measurements
4. Process the results to update your tracking system

**Client Responsibility:** Your system must store all weight measurements and provide them for replay.

### 7. Response Format
All responses follow API v2 format with `success`, `data`/`error`, and `meta` fields. Always check `success` first.

### Common Issues

**Issue: "action" vs "operation"**
- **Problem:** Documentation used "operation" but code expects "action"
- **Solution:** Use "action" in all payloads

**Issue: Unsupported unit "pounds"**
- **Problem:** Full word units are not supported
- **Solution:** Use abbreviations: "lb" or "lbs" instead of "pounds"

**Issue: Missing nested "body" field**
- **Problem:** API v2 requires request data in "body" field
- **Solution:** Structure as `{"action": "...", "user_id": "...", "body": {...}}`

**Issue: Unexpected response format**
- **Problem:** Expecting old format without success/data/meta wrapper
- **Solution:** Parse API v2 format: check `.success`, then access `.data` or `.error`

**Issue: Replay without measurements**
- **Problem:** Expecting Lambda to store all measurements for replay
- **Solution:** Client must store and provide all measurements in replay request

## API Changes

### v2.1.0 - Pattern 2 Replay Removal (2025-10-02)

**REMOVED: Automatic replay endpoints**

The following endpoints have been removed:
- `replay_check` - Check if replay should trigger
- `replay_execute` - Execute replay for a window

**Migration Guide:**

Instead of the two-step Pattern 2 workflow:
```bash
# OLD (Pattern 2 - REMOVED)
# Step 1: Check
aws lambda invoke --payload '{"action": "replay_check", ...}'
# Step 2: Execute
aws lambda invoke --payload '{"action": "replay_execute", ...}'
```

Use the single `replay` endpoint (Pattern 1):
```bash
# NEW (Pattern 1 - Current)
aws lambda invoke --payload '{
  "action": "replay",
  "user_id": "user-123",
  "body": {
    "replay_from_timestamp": "2025-09-25T00:00:00Z",
    "measurements": [
      /* Query your database for measurements */
    ]
  }
}'
```

**Key Changes:**
- Client must store all weight measurements
- Client queries measurements for replay window
- Client provides measurements in replay request
- No 30-measurement limit (was limitation of Pattern 2)
- Simpler API with fewer endpoints
